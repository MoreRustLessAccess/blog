While Envoy Gateway is meant to be used as a reverse proxy for services hosted inside your Kubernetes cluster, the only thing stopping you from pointing it at external services is a bit of Kubernetes wrangling.

Your first proxied endpoint

You start by setting up an HTTPRoute and Service like normal, with the only difference being that the Service should not have any selector set.

The reason that you don't set a selector on the Service is that the selector only supports selecting pods - not external services.

Now that you have created the HTTPRoute and Service, you should be able to make a request through the HTTPRoute - though you will get an error similar to "no healthy upstream" because we don't have any upstreams (EndpointSlices) registered. This is something Kubernetes usually registers for us when we give a selector to the Service. However, since we don't specify a selector, we have to create our own EndpointSlice.

Note that the value of the kubernetes.io/service-name label needs to be the same as the name of your Service.

Oh no, TLS!

In a typical Kubernetes setup, your services operate over HTTP while TLS is the responsibility of the gateway. If your backend uses HTTPS, this assumption breaks. To support this, we need to opt in to using TLS to the endpoint via a BackendTLSPolicy.

Note that the hostname here needs to match the hostname on the certificate, as the standard does not allow implying it via the endpoint IP.

What about self-signed certificates?

If your backend uses a certificate that isn't trusted by your system's trust store, your CNI will fail to connect to it, and your request will fail. To support this, you need to add the root authority that signed your certificate to your BackendTLSPolicy.
